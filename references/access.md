# Give the factory enough access to build itself

Start with one owner-controlled admin box. Agree on the account, project scope, monthly budget, and shipping authority once. Within that grant, let the agent configure and repair its tools and infrastructure. The initial goal is an agent that can do useful work, not a completed enterprise access system.

Use the owner's signed-in browser or console when available. The agent should navigate settings and perform authorized setup itself. The owner completes authentication, multifactor challenges, enrollment, and billing steps that require them. If browser tooling is unavailable, give the owner the exact page, selections, destination for the credential, and reason. Do not make them research the setup on the agent's behalf.

## Bootstrap the five connections

1. **AWS:** sign in through the owner's console, CloudShell, or federated administrator session. Create an EC2 admin role and instance profile with the authorized account administration permissions, then launch the box with that profile. AWS tools on the box obtain temporary credentials automatically. Enable Session Manager, persistent encrypted storage, and the required outbound connectivity. Keep root recovery and multifactor authentication with the owner; never create root access keys. IAM administrator authority does not replace root-only operations. See the [concrete EC2 path](../examples/bootstrap/provision.md), [IAM guidance](https://aws.amazon.com/iam/resources/best-practices/), and [Session Manager permissions](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-getting-started-instance-profile.html).
2. **GitHub:** run `gh auth login --web` as the box user that runs the agent, then configure Git access with `gh auth setup-git`. Use an owner who already has the agreed repository or organization authority, and request additional permissions for actual administration tasks. Browser login alone does not grant every organization permission. Tokens cannot exceed their owner's access, and fine-grained tokens have resource and API limits. For durable organization automation, graduate to a GitHub App with explicit installation permissions. Inspect credential storage: `gh` can fall back to a plaintext file if no credential store exists. See [CLI login](https://cli.github.com/manual/gh_auth_login) and [token capabilities](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens).
3. **Cloudflare:** select the owner's intended account. Super Administrator includes member and billing control; Administrator does not. For bootstrap, create an account-owned API token with the broad supported permissions the owner authorized, then record its scope and expiry. Account tokens require token-provisioning authority or Super Administrator status, cannot exceed the creator's permissions, and do not support every API. Use the documented user-token route for a required unsupported operation instead of promising a universal supertoken. Later issue account, zone, or workload-specific tokens. See [account roles](https://developers.cloudflare.com/fundamentals/manage-members/roles/) and [account tokens](https://developers.cloudflare.com/fundamentals/api/get-started/account-owned-tokens/).
4. **PlanetScale:** sign in to the intended organization, then create a named service token and assign the authorized organization and database permissions. Organization admins can grant permissions across current and future databases; those broad grants cannot be removed for just one database. `create_databases` gives the token permissions on the databases it creates. Store both the token identifier and secret. This controls the provider API, not SQL authentication. Create separate PostgreSQL roles for applications and migrations; the managed default role is not an unrestricted PostgreSQL superuser. See [service tokens](https://planetscale.com/docs/api/service-tokens) and [SQL roles](https://planetscale.com/docs/postgres/connecting/roles).
5. **Coding accounts:** install the selected clients from their official docs. Run their current supported sign-in flow on the box, for example `claude auth login` or `codex login --device-auth`; use Cursor's documented client flow. The owner completes the account authorization. Retain each client's native credential management rather than copying browser cookies or another person's session. A subscription sign-in is separate from a product API key. Check headless workers independently. Finish by obtaining one actual response from the chosen agent in the intended runtime; a status command only proves local authentication state. See [Claude authentication](https://code.claude.com/docs/en/authentication), [Codex authentication](https://developers.openai.com/codex/auth/), and [Cursor CLI authentication](https://cursor.com/docs/cli/reference/authentication).

## Capture secrets without making a transcript of them

Prefer direct capture into an approved credential manager or the account's Parameter Store or Secrets Manager. If that is unavailable during bootstrap, use an owner-only directory with mode `0700` and credential files with mode `0600` on encrypted storage. Treat this as real credential storage with backup and rotation responsibilities, not an example file to commit. A fully privileged box user can read those files; file permissions do not isolate secrets from its administrator.

Use a trusted secret-entry surface or hidden terminal input. Avoid putting secrets in command arguments, shell history, tool output, screenshots, chat, or run records. If the only available browser/terminal tool exposes the new token to its transcript, hand off that capture step to the owner. Record only the provider, credential reference, grants, owner, expiration, rotation method, and which runtime can retrieve it. Never store the secret in the inventory.

Provider login is not the acceptance test. Make a harmless real request against each required service from the process that will use it. A read proves only that read capability; confirm write authority through reviewed permission configuration and the first authorized setup operation. Mark untested capabilities unknown. The [example doctor](../examples/bootstrap/README.md) starts with AWS and GitHub; add Cloudflare or PlanetScale when the project selects them.

## Evolve into separate daily and administrative access

Before customer production data, more teammates, unattended jobs, or unrelated projects share this setup, revisit the boundary. Keep the admin box as a controlled administration path. Give daily development boxes and application services narrower roles and credentials. Do not distribute the bootstrap tokens to every worker.

Use AWS Organizations for management, staging, production, and unrelated workload accounts when those boundaries are needed. Put provider tokens and runtime secrets in the account and environment that need them. Grant cross-account assumption explicitly, with both source permission and destination trust. Separate applications' SQL roles from database-management credentials. Rotate or revoke broad credentials when replacing them, then prove allowed operations succeed and forbidden account, environment, and secret reads fail. The [account and daily-role example](../examples/bootstrap/accounts.md) shows one way.

Account names, role names, and secret prefixes are not isolation by themselves. An IAM administrator can usually modify permissions in its own account. Parameter Store recursive reads can expose descendants through an allowed parent path, and the default Session Manager managed policy includes wildcard parameter reads. Prefer narrow grants, account separation, and appropriate KMS controls rather than a broad grant with an incomplete deny. See [AWS account separation](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_best-practices.html), [Parameter Store restrictions](https://docs.aws.amazon.com/systems-manager/latest/userguide/ps-restrict-parameter-access.html), and [the Session Manager managed policy](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/AmazonSSMManagedInstanceCore.html).
