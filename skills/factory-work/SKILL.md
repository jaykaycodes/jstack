# Deliver useful software

Use the project's owner policy and [shared baseline](../grow-factory/assets/baseline.md). Follow the [work loop](../grow-factory/references/work-loop.md), scaling the artifacts to the change. A tiny fix needs less planning than a migration.

1. Define the observable outcome and proof surface. Gather available facts before asking for decisions. Reproduce a bug where it fails.
2. For a substantial change, write a short plan with boundaries, decisions, implementation slices, and checks. Settle product decisions before dependent work.
3. Build the smallest coherent slice. Use [factory-stack](../factory-stack/SKILL.md) when starting a project or changing a technology choice. Preserve established project conventions unless the task warrants migration.
4. Delegate bounded scouting, implementation, or review when it helps. Use the [role contracts](references/roles.md), with a clear integration owner and exact done check.
5. Exercise the actual behavior and inspect the result. For substantial work, use fresh-context review against the request, changed revision, surrounding code, and raw proof. Resolve material findings and invalidate affected evidence after edits.
6. Ship within granted authority. Update the knowledge that the change makes inaccurate. Return the outcome, evidence, gaps, and exact remaining human action, then stop owned resources.

The work loop also defines architecture checks, a small project knowledge base, and a handoff that another client can resume. Use those when the work needs them rather than creating separate ceremonies for every edit.
